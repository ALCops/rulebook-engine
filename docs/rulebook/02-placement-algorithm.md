# Placement algorithm

Generated by `tools/rulebook/Build-Matrix.ps1` from `inventory/placements.json` and the fallback rule tables inside that script, printed so the documentation cannot drift from the matrix. To change a placement, edit the entry of the id in `inventory/placements.json` and rebuild (D60, DR-022).

## 1. How an id is placed

For every id in the inventory:

1. **Placements entry.** The entry of the id in `inventory/placements.json` gives the ladder, the `CI` and `vNext` actions with their own justification, and the justification of the row. `Basis` is the decision record the entry names, `DR-022` when it names none. Every id has an entry; check V15 fails on an id without one.
2. **Fallback rows, only for an id without an entry** (an inventory refresh adds ids before they are reviewed): the override rows `OV-nn` (explicit ids), then the family rows `F-nn` (by `Family` or flag), then the decision rows `D-nn` (by analyzer, default severity and enablement); the first matching row gives the ladder, the justification and the `Basis` token, and the stage rules `S-n` fill the stage columns unless the row pins them. `Build-Matrix.ps1` prints these ids with the proposed ladder; the proposal is a starting point for the review, not a placement.

The resolution recipe in [00-conventions.md](00-conventions.md) turns a row into 12 cells, one per level and stage, keyed `<level>.<stage>` by slug (`essential.default`, `recommended.ci`). In an organization repository the `CI` and `vNext` columns become the stage files `stages/ci.json` and `stages/vnext.json`, applied on top of every level (D27); the `Default` column is always `=` and has no file. There is no target dimension: every rule has one ladder for every AL project (D21).

Ladders are written `Essential/Recommended/Strict/Complete`. `native` stands for the ladder derived from the author severity: Error -> `Error/Error/Error/Error`, Warning -> `None/Warning/Warning/Warning`, Info -> `None/Info/Warning/Warning`, Hidden -> `None/Hidden/Info/Info`.

## 3. Level and severity intent

Every entry is a judgment of what the rule catches and what breaks or degrades when it is ignored. The levels say what the judgment is for:

| Level | What is on | Severity rule |
|---|---|---|
| Essential | The bare minimum a project cannot ship without: definite runtime failures, deployment blockers of either kind of extension, compiler future errors, security leaks and broken configuration. It stays usable without `AppSourceCop.json`: no marketplace check is above None here. | Error for a definite defect, Warning for the rest. |
| Recommended | What a healthy project runs: the Rulebook opinion per rule, which may sit above or below the author severity when the benefit justifies it. | Error for a definite defect; style, naming and advice at most Warning. |
| Strict | The quality gate: advisory rules that a clean project satisfies become Warning. | As Recommended. |
| Complete | Everything the analyzers can tell you, opt-in rules included, except LC0089i and contradiction losers. | No Error for an opt-in rule. |

Error is placed only when the rule proves a definite defect (a runtime failure, data loss, a security leak, a deployment or submission blocker) and the justification names it. Style, naming and advice stop at Warning. A rule its author ships disabled is never Error, and `vNext` raises to Error only a rule that is already Warning or Error on every level where it is on. Ladders never get weaker from one level to the next (V3, V11).

## 4. Project kinds and twins

The matrix does not know whether a project is a per-tenant extension or an AppSource app (D21). Both Microsoft cops are active, so a per-tenant project sees the AppSourceCop blockers (AS0084 and AS0013 on id ranges, the marketplace manifest checks from Recommended) and an AppSource project sees the PerTenantExtensionCop blockers (PTE0001, PTE0002, PTE0009, PTE0013, PTE0024). The project opts out of the side that does not apply: by disabling a cop in `al.codeAnalyzers`, by `suppressWarnings` in `app.json` (which works for a rule that is not listed in the endpoint, D22), or by a rule in its project ruleset file. The user documentation of the Rulebook template (`docs/pte-or-appsource.md`) carries the ready-made lists. DR-018 and DR-019 record the cop-specific placements.

The 17 twin pairs (identical check in both cops, listed in [overlaps.md](overlaps.md) and exported to `matrix/twins.json`) share one ladder, one pair of stage columns and one justification. An organization that builds only one kind of extension picks a side with the `twins` setting of its Rulebook repository (`both`, `appsource` or `pte`); the generator writes the losing side at `None`. DR-020 records the policy, DR-022 the shared ladder.

## 5. Stages

`CI` never blocks on what a team cannot fix in the same change; an entry there lowers the level action and says why. `vNext` previews what the next platform breaks; an entry there raises the level action and says why. A stage entry never enables an id the level left at `None` (see the resolution recipe in [00-conventions.md](00-conventions.md)); this binds every stage file, shipped or custom (D27).

## 6. Justification

Every matrix row carries the justification of its placement: one sentence of 1 to 200 characters, without a pipe or a line break, that says what the rule catches and why it sits where it sits. The generated level file entries copy it verbatim into the `justification` property. A stage entry carries its own sentence in the `CIJustification` or `vNextJustification` column, which the stage file entry copies; the column is `=` when the stage keeps the level action.

## 10. Fallback: stage rules

- **S-1** The default stage equals the level action; developers see exactly what the pipeline sees. It has no stage file.
- **S-2** CI = Info for diagnostics a team cannot always fix in the same change: family obsolete (F-05) and AL0603, AL1026, AL0472, AL0473, AL0479, AL1029, AL1030 (implicit conversions, XML validation, translation file mismatches).
- **S-3** vNext = Error for family future-error (F-04) and Warning for family obsolete (F-05); everything else equals the level action.
- **S-4** A stage entry never enables an id the level left at None (see the resolution recipe in 00-conventions.md); this binds every stage file, shipped or custom (D27). New ids that appear in a prerelease compiler are a scan-time concern of WP08, not of the matrix.
