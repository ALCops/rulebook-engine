# D45. The scan keeps one living pull request and records every package version

- **Status:** Accepted
- **Date:** 2026-10-07

- **Decision:** the diagnostic scan publishes its result as one pull request per base branch on the fixed branch `scan-diagnostics/<base>`, which every run rebuilds from the base head as one commit with the full current result, pushes with `--force-with-lease` and describes by replacing the title and body of the open pull request (or opening it), and it does so for every new package version, also when that version brings no new id and no changed default.
- **Rationale:** a scan runs every day while a reviewer may leave its pull request open for a week; one pull request that always shows the current state of both packages is what a reviewer can act on, while a pull request per run would pile up overlapping changes to the same catalog and quarantine files that conflict with each other as soon as one is merged. Rebuilding from the base head keeps the branch mergeable after other pull requests and makes the body (counts, new ids, effective diff) describe exactly what the branch holds. The lease push rejects a commit someone pushed between the moment the run read the branch head and its push; it does not cover the planning before it, so the plan also records the head of its checkout and the publish step refuses a base branch that moved since, and a push to the scan branch before the run is replaced (the body says not to push there). The branch name, not the title, identifies the pull request, so the title can carry the counts and change from run to run. A record run without new ids is still a pull request because the catalog's `lastSeenVersion` and `catalog/scan-state.json` move; skipping it would leave the state behind and make the next real change scan versions it has already seen.
- **Rejected:** a timestamped branch per run with a title guard like the update (WP07): the update has one template version to apply, the scan has a stream of package versions, and a guard would either drop newer results or open duplicates; skipping record-only runs (the scan state would lag the packages and every run would repeat the downloads); a plain `--force` push (silently discards a commit someone pushed to the branch); appending a commit per run to the open branch (the branch drifts from the base, conflicts with merged work, and the body no longer matches the diff).
- **Consequences:** `Rulebook.GitHub` gains `PATCH` in `Invoke-GitHubApi`, `Find-GitHubPullRequestByHead`, `Update-GitHubPullRequest` and `Publish-GitHubChange -Force` (lease push, also for the fallback of a refused direct commit). `Publish-RulebookScan` returns `pull-request` or `pull-request-updated`, and closes an open scan pull request when the base already holds the result or it went in as a direct commit. The pull request body says not to push to the branch. The title scheme is `Scan diagnostics: <counts> (<label> <version>, ...)`, with `... recorded, no new diagnostics` for a record run. With `commitOptions.createPullRequest: false` a scheduled run commits directly, as the update does. Contract: [reference/scan-mechanics.md](../reference/scan-mechanics.md) section 7.
- **Affects:** WP08 ([#10](https://github.com/ALCops/rulebook-engine/issues/10)).
