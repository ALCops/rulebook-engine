# D38. Release notes are generated from pull request labels

- **Status:** Superseded by D52 (2026-10-10)
- **Date:** 2026-10-03

- **Decision:** the engine's release notes are generated by GitHub from the merged pull requests, sorted into sections by label through `.github/release.yml`; the deploy step turns the same text into the template's `RELEASENOTES.copy.md` with `POST /repos/{owner}/{repo}/releases/generate-notes`, and no release-notes file is maintained by hand.
- **Rationale:** the pull request already carries the title, the link and the author, so a hand-written line repeats it and drifts. The generator is built into GitHub, needs no third-party action and no commit format, and the deploy step can call it for any tag range, so the text a GitHub Release shows and the text an organization's update pull request shows are the same.
- **Rejected:** a hand-maintained `RELEASENOTES.md` (AL-Go style; one more file to edit and conflict on in every pull request); release-please (needs conventional commit messages and its own tooling); release-drafter (a third-party action with write access for what GitHub does natively).
- **Consequences:** every pull request carries one release-note label (`enhancement`, `bug`, `documentation`, `dependencies`, or `skip-changelog` to leave it out) and a title that reads as a release line. A pull request that changes level content names the diagnostic ids and the file in its title, so the organization's update pull request still says what moved; WP13 keeps that rule. Definition of done item 7 in the README is reworded accordingly. The labels `dependencies` and `skip-changelog` are created by WP00.
- **Affects:** WP07, WP13.
