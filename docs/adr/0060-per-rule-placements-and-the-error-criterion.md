# D60. Every diagnostic is placed on its own, and Error marks a definite defect

- **Status:** Accepted
- **Date:** 2026-11-16

- **Decision:** the level and stage placement of every diagnostic is a judgment about that rule, recorded by hand in `docs/rulebook/inventory/placements.json` with its ladder, its `CI` and `vNext` actions and one justification sentence per row and per stage entry; `Error` is placed only where the sentence names a definite defect (a runtime failure, data loss, a security leak, a deployment or submission blocker), never for style, naming or advice, and never for a rule its author ships disabled.
- **Rationale:** until beta.8 the matrix came from 31 generic rows in `tools/rulebook/Build-Matrix.ps1`. Every one of the 628 diagnostics inherited the ladder and the sentence of the row it matched, so the published justifications were about 30 shared texts such as "Author severity from Recommended; D-06", and Recommended was by construction the analyzer author's default rather than an opinion. Error was confined to a family whitelist and to the Error defaults of PerTenantExtensionCop and AppSourceCop, which left definite defects at Warning (a table no permission set covers, a CalcFields on a field that is neither FlowField nor Blob) and kept a broken integration (PC0025) at Error. The owner asked on 2026-11-16 for every rule to be looked at on its own: what it catches, what breaks or degrades when it is ignored, and from that an explicit decision per level and per stage, each with its own reason. The level intents stay (Essential: cannot ship without; Recommended: what a healthy project runs; Strict: the quality gate; Complete: everything the analyzers can tell you); the content under them becomes an opinion. One file next to the inventory keeps the decision and its reason in one place, reviewable line by line in a pull request.
- **Rejected:**
  - **More generic rows** (finer families, more override rows): still one text per row, and every exception becomes a new row; the reader of a level page still cannot tell why a rule sits where it sits.
  - **Justifications in the inventory annotations:** `annotations.json` describes what a rule is (family, configuration gates, overlaps); mixing in what Rulebook decides about it would blur the inventory refresh with the review.
  - **A JSON schema for `placements.json` under `schemas/`:** that folder is the published contract of an organization repository; this file is engine-internal and is validated by `Build-Matrix.ps1` and check V15.
  - **A "debatable" list for unsure rules:** an unsure rule keeps the author's default and its sentence says so; a separate list would be a second place to look.
  - **Keeping Error for the runtime family and the two Microsoft cops' Error defaults only:** it treats a severity chosen by an analyzer author as the definition of a defect. The Error criterion asks the same question of every rule.
- **Consequences:**
  - `Build-Matrix.ps1` reads `placements.json`; the generic rows survive only as the proposal for an id without an entry, which the script lists, and check V15 fails until the id is placed. An inventory refresh therefore places its new ids in the same pull request.
  - The matrix gains the columns `CIJustification` and `vNextJustification` (twelve columns), and `Basis` is a decision record (`DR-022` unless an entry names an older record). `Rulebook.Template` writes the stage sentence into the stage files.
  - Checks: V4 (opt-in never Error; `vNext` Error only on Warning or Error), V6 (both sides of a twin pair share one ladder and one pair of stage columns), V7 (fallback only, with a review aid for placed rules), V8 (decision-record basis), V9 (1 to 200 characters, stage sentences), V12 (fallback only) and the new V15.
  - Guardrails the review keeps: Essential stays usable without `AppSourceCop.json` (no marketplace rule above None there, DR-019); ladders stay monotonic and cumulative; LC0089i and contradiction losers stay None.
  - Every justification string of the shipped level and stage files changes, and the review moves 142 diagnostics in at least one cell. Organizations receive both through their next update pull request (beta.9), which shows the effective diff per endpoint before they merge. An organization's own `Rulebook-Settings.json` keeps its old level and stage descriptions until it edits them.
  - Decision record DR-022 in `docs/rulebook/decisions.md` records the review and its outcome; DR-009, DR-012, DR-013, DR-015, DR-016, DR-018, DR-019, DR-020 and DR-021 carry a Note on how their reach changed.
- **Affects:** the per-rule placement pull request (`review/per-rule-placements`); every later inventory refresh; D16 (level content in `docs/rulebook/`) and D27 (delta files) stand unchanged.
