# D55. The apply workflow gates on push permission: the issue author, and the editor of a body edit

- **Status:** Accepted
- **Date:** 2026-10-18

- **Decision:** the Apply Rulebook Change workflow applies a change set only when the issue author, and the editor of a body edit, can push to the repository: `GET /repos/{owner}/{repo}/collaborators/{author}/permission` answers `admin` or `write` (as GitHub documents it, maintain is reported as write and triage as read); an account other than the author that edited the issue body must pass the same check; anyone else gets one comment and the issue is closed as not planned (an editor refusal leaves the issue open), before the body is read. This amends the mechanism of D34 and keeps its intent: the organization's own permission model, no approval label, the pull request as the review.
- **Rationale:** `author_association` `COLLABORATOR` includes read-only outside collaborators (GitHub-documented, as is everything this record says about the endpoint; the WP15 live run observes it), so the literal D34 gate would let an account that cannot push to the repository change its endpoints through the workflow, in direct-commit mode without any review. The permission endpoint answers the question that matters (could this person make the change themselves?), reflects the highest grant across the repository, its teams, the organization and the enterprise, and needs only metadata read, which the plain workflow token has. A 404 (no collaborator, an unknown login, or a token that cannot read the collaborators, which would refuse everyone) reads as `none`, so the gate fails closed; any other failure of the call stops the run without applying anything.
- **Rejected:** the literal `author_association` check of D34 (`MEMBER` and `COLLABORATOR` say nothing about write access: an organization member may have only read on this repository, a read-only collaborator is `COLLABORATOR`); both checks together (the association adds nothing the permission does not decide, and two checks that can disagree need a rule for when they do).
- **Consequences:** bots and GitHub Apps are refused unless the endpoint reports write for them (an issue opened with an installation token is expected to be refused). The gate checks the author of the issue, so a maintainer's edit of a stranger's issue is still refused; the maintainer opens their own issue instead. It checks the editor too, the sender of an `edited` event read from the run's event file (not a workflow input, so an older workflow copy cannot lose the check; an edit without a sender is `none`): a triage-role user may edit another user's issue body, and without that check the edited change set would be applied under the author's authority, in direct-commit mode without any review. A run whose event body differs from the body the API returns stops without a verdict (the body was edited again; the newer edit's run judges it), so a run never applies a body its sender did not write. The author refusal is `Only repository collaborators with write access can submit or edit Rulebook changes.` and closes the issue as not planned; a refused editor gets a comment that names the account and the issue stays open for its author. The issue is read again through the API on every run (the event payload can be stale on `edited`), and the gate runs before the label, the duplicate guard and the parser. The docs say "only an author who can push to the repository gets the change applied" instead of "collaborators".
- **Affects:** WP15 ([#17](https://github.com/ALCops/rulebook-engine/issues/17)).
