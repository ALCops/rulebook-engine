# D53. Template main is the release, preview the bleeding edge, tags the pin, and deprecations replace majors

- **Status:** Accepted
- **Date:** 2026-10-11

- **Decision:** a release writes the engine's `template/` to `ALCops/rulebook@main` (the default branch) with the engine references rewritten to the floating engine branch `v<major>` and tags it `vX.Y.Z`, the refresh writes it to `ALCops/rulebook@preview` with the template references rewritten to `preview`, an organization pins a release by a tag in `templateUrl`, and a breaking change ships as a dated deprecation instead of a new major; D53 fully supersedes [D52](0052-releases-are-a-floating-major-branch-cut-from-hand-written-release-notes.md) and restates what stays.
- **The model:**

  | Repository | Ref | Written by | Content |
  |---|---|---|---|
  | `ALCops/rulebook-engine` | `main` | pull requests | development |
  | `ALCops/rulebook-engine` | `v1` (floating), tags `v1.x.y`, a GitHub Release per tag | the Deploy workflow | the released engine; every release moves `v1` (unchanged from D52) |
  | `ALCops/rulebook` | `main` (the default branch), tags `v1.x.y` | the Deploy workflow | `template/` with the engine references at `@v1` and `/v1/`, the template references (`templateUrl`, `rulebook/blob\|raw\|tree/`) at `main`, `.github/RELEASENOTES.copy.md`, the kept files |
  | `ALCops/rulebook` | `preview` | the Refresh Template workflow | `template/` with the engine references at `main` and the template references at `preview` |

  - "Use this template" gives a repository whose only branch is `main` and whose `templateUrl` ends in `@main`; the update follows the head of the template's `main`, which is always the latest release.
  - The pin: `templateUrl` ending in a release tag (`@v1.0.0`) with `update.schedule` at `null`. The update resolves `@<ref>` as a branch first and, only when the branch answers 404, as a tag ([#108](https://github.com/ALCops/rulebook-engine/pull/108)); a branch wins over a tag of the same name.
  - What comes next: `templateUrl` ending in `@preview`. The canary rulebook follows it, so its workflows run the engine at `main`.
  - Restated from D52: the top `## vX.Y.Z[-pre]` heading of a hand-written `RELEASENOTES.md` is the version and its section the notes; every pull request adds its line under it; the deploy refuses a tag that exists on either repository; the GitHub Release on the engine carries the section; every deploy writes `.github/RELEASENOTES.copy.md`, so an engine-only release still produces an update pull request whose body is the changelog; the deploy is a `workflow_dispatch` workflow with a `dryRun` input that authenticates as the ALCops GitHub App and commits directly. Code names no release branch: the actions build their URLs from the ref they run at (`Get-RulebookEngineRef`), and the user docs URL maps that engine ref to a template ref (`Get-RulebookDocsUrl`: `v<n>` to `main`, `main` to `preview`, a release tag to the same tag, a commit sha to `main`, anything else to `preview`).
- **Deprecations instead of majors:** a change that would break an organization (a settings key renamed or removed, a file changing its class, a change of the published endpoint URL layout, a change of the secret contract) ships as a deprecation. The engine honours the old form and prints a warning annotation that names the replacement and the removal date; `RELEASENOTES.md` gets a "Deprecations" line under the version that introduces it; the date is at least one release and some months away; after the date the old form is an error that names the replacement. Support is latest only: fixes land in the next release, never in an old tag. The engine's floating `v1` lives as long as the action contract (the `uses:` inputs, the outputs, the `GHTOKENWORKFLOW` secret); its major is bumped only if that contract breaks, and then through the same deprecation route first. Versions stay `v1.x.y`. The deprecation helper, its registry and a user-facing `deprecations.md` page are written with the first deprecation, not before.
- **Rationale:** decided in the [#104](https://github.com/ALCops/rulebook-engine/issues/104) planning interview of 2026-10-11.
  - *"Use this template" names the new repository's only branch after the template's default branch.* With D52's default branch `v1`, every new organization got a `v1` branch, the shipped workflows (`branches: [ main ]`) stayed silent, and after a rename to `main` the `github-pages` environment, whose deployment branch policy had been created for `v1`, refused the deploy (observed on `Arthurvdv/rulebook-e2e-release`, 2026-10-11). A template whose default branch is `main` gives `main`, which is what the shipped workflows and the Pages environment expect.
  - *AL-Go's model.* microsoft/AL-Go has no version check in its update: `Actions/CheckForUpdates/CheckForUpdates.ps1` compares and records `templateSha` only (lines 52 to 64). Its compatibility comes from three mechanics, all observed on microsoft/AL-Go@main on 2026-10-11: a deprecated settings key keeps working with a warning that says it will become an error (`Actions/CheckForUpdates/CheckForUpdates.HelperFunctions.ps1` line 545, `Trace-DeprecationWarning ... -DeprecationTag "_workflow_Schedule" -WillBecomeError` for the old `<workflow>Schedule` key under the comment "REPLACE WITH ERROR AFTER October 1st 2025", and line 1108 for `unusedALGoSystemFiles`); `DEPRECATIONS.md` lists each deprecation under "Changes in effect after <date>" and opens with "Old AL-Go versions might stop working any time", so only the latest version is supported and fixes ship in the next one; `RELEASENOTES.md` has a "Deprecations" section in each release that introduces one (v6.3, v6.4, v8.1), and its one "Breaking changes" section (v3.3) names the replacement of what stopped working. Rulebook has no organization outside the maintainers' test repositories today, so a breaking change is acceptable now, and the deprecation route keeps it acceptable later without a second content line.
  - *Tags are the pin.* Once the template has no `v1` branch, a tag is the only ref that holds a release still. The day the engine ever moves on, an organization on 1.x points at its last 1.x tag. Tags are protected on both repositories (`protect-release-tags`), so a pinned ref never moves.
  - *The engine keeps its floating `v1`, the template has none.* The engine follows the GitHub Actions idiom (`actions/checkout@v4`): a fix reaches every organization's workflows at their next run without a pull request, which is the reason the engine is a separate repository (D2). Template content reaches an organization only through the update pull request, so a floating template branch adds nothing to `main` but the "Use this template" trap above.
  - *Two rewrite targets.* The engine references and the template references now point at different refs: on a release the engine at `v1` and the template at `main`, on a refresh the engine at `main` and the template at `preview`. `Rulebook.Deploy` has one pattern per repository; they match disjoint positions because `-engine` sits between `rulebook` and the `/` or `@` the template pattern needs.
- **Rejected:** a rename step after "Use this template" (one more thing every organization must get right, and the Pages environment keeps the old policy); keeping a template `v1` next to `main` as a second release branch (two branches with the same content to keep in step, and the default branch decides what "Use this template" gives anyway); `next` as the name of the bleeding-edge branch (AL-Go calls it `preview`, and an organization that knows AL-Go knows the word); AL-Go's per-release engine branches (every engine fix would need an update pull request per organization; the floating `v1` delivers it at the next run); a refusal gate on the engine major, the open point of #104 (with deprecations there is no second major to guard against; the gate would only add a failure mode); amending D52 in place (D52 describes what WP13 shipped and the live releases beta.1 and beta.2 were cut under it; a new record keeps that history readable).
- **Consequences:** D52 is superseded; its text stays. `Rulebook.Deploy` has two patterns, `Convert-DeployReference` and `Update-DeployReference` take `-EngineBranch` and `-TemplateBranch`, `Get-DeployPlan` has `EngineBranch` and `TemplateBranch` instead of `Branch`, a release clones and pushes template `main` (the bootstrap of a missing branch is gone), a refresh writes `preview` and creates it from `main`'s head on its first run, and the summary names both targets in both modes. `Get-RulebookDocsUrl` of `Rulebook.Common` and the two standalone scripts map the engine ref to a template ref, so the token and AL project links printed at `@v1` point at the template's `main`. The update resolves a tag in `templateUrl` (`Get-GitHubRefSha`, #108); switching `@main` to a tag counts as another template URL, so `templateSha` is not reused, as for any other change of `templateUrl`. [docs/releasing.md](../releasing.md) is rewritten around the model, with section 5 as the deprecation procedure. Writer rule for `template/docs`: the full template URL (`https://github.com/ALCops/rulebook@main`, `ALCops/rulebook/blob/main/...`) is rewritten to `preview` by the refresh, so prose writes it only where that is right (the form default in `updating.md`); where `main` means the release literally, prose writes the bare `@main`, and a Deploy test checks `versioning.md`. The compatibility CI job of [#106](https://github.com/ALCops/rulebook-engine/issues/106) now checks the deprecation rule and the promise of releasing.md section 4 rather than a major contract. The first deprecation brings the helper, its registry, a `deprecations.md` page in `template/docs/` and a "Deprecations" section in the notes. The settings of `ALCops/rulebook` change by hand (releasing.md section 7): the default branch becomes `main` (the `protect-main` ruleset targets the default branch, so it protects `main`, which the release pushes as the App), the `protect-release` ruleset is deleted, `protect-release-tags` stays, and the `v1` branch is deleted once the repositories created from it are gone; the engine's settings do not change. The 1.0 checklist ([#18](https://github.com/ALCops/rulebook-engine/issues/18)) has no v2 item.
