# D52. Releases are a floating major branch cut from hand-written release notes

- **Status:** Accepted
- **Date:** 2026-10-10

- **Decision:** a release moves the floating branch `v<major>` (`v1` now) to a commit of engine `main` and copies the engine's `template/` to `ALCops/rulebook@v1` with one rewrite rule, tags both repositories `vX.Y.Z` and takes the version and the notes from the top heading of a hand-written `RELEASENOTES.md`, while `ALCops/rulebook@main` carries the engine's `template/` verbatim for the canary rulebook.
- **Rationale:** organization workflows reference `ALCops/rulebook-engine/actions/<Name>@v1`, so an engine fix reaches every organization at its next workflow run without an update pull request, which is the reason the engine is a separate repository (D2); template content still arrives through the update pull request, and every deploy writes `.github/RELEASENOTES.copy.md` so even an engine-only fix produces a small update pull request whose body is the changelog. Details, as decided on [#15](https://github.com/ALCops/rulebook-engine/issues/15) on 2026-10-10 (the O3 comment) and in the WP13 planning interview of the same day:
  - *Branches.* `ALCops/rulebook@v1` is the release branch and the default branch, so "Use this template" and the update follow `@v1`. `ALCops/rulebook@main` is refreshed on every push to engine `main` that touches `template/`, with only `templateUrl` rewritten to `@main`; the maintainer's own rulebook follows it (`templateUrl` at `@main`) and is the canary that runs unreleased engine code. There is no `preview` branch and no frozen minor branch; an organization that wants to freeze content sets `update.schedule` to `null`.
  - *One rewrite rule.* The engine's `template/` says `main` in every engine reference (the five `uses:` lines, the `$schema` URLs, the script URLs, the user docs links); the release deploy rewrites every `ALCops/rulebook` and `ALCops/rulebook-engine` reference that names `main` to the target branch. The engine's `v1` is a plain move of `main` with no rewrite commit, so the engine itself never names a release branch in code: the actions build the schema, script and docs URLs they print or write from the ref they were called with (`Get-RulebookEngineRef` of `Rulebook.Common`: `GITHUB_ACTION_REF`, else `main`), and the two standalone scripts take `-Ref` with the literal current major as the default, raised by hand at a major (spin-off [#63](https://github.com/ALCops/rulebook-engine/issues/63)).
  - *Version and notes.* The top `## vX.Y.Z[-pre]` heading of `RELEASENOTES.md` is the version; the deploy derives the branch from the major and refuses a tag that exists on either repository. Every pull request adds its release line under that heading (AL-Go practice); the first pull request after a release adds the next heading. The GitHub Release on the engine carries that section as its body; the template repository gets the tag.
  - *Majors.* Latest major only: the day `v2` ships, `v1` is frozen and the template's default branch becomes `v2`; pinned organizations opt in by editing `templateUrl`. A new major is triggered by content, when the update pull request alone cannot carry an organization across safely (a settings key removed or renamed, a file moving between file classes, the published endpoint URL layout, the secret contract), not by the calendar. Within a major a new Validate check starts as a warning, settings keys are only added and file classes do not change: a written policy, not a CI job.
  - *Deploy.* A `workflow_dispatch` workflow of the engine (input `dryRun`) authenticates as a GitHub App owned by the ALCops organization, installed on both repositories, and commits directly (pull requests are disabled on `ALCops/rulebook`); the template repository is written only by the deploy and the refresh. The first deploy is the WP13 acceptance run with a prerelease tag (`v1.0.0-beta.1`); `v1.0.0` follows at the 1.0 checklist.
- **Rejected:** AL-Go's frozen `major.minor` branches (every hotfix would need an update pull request per organization; AL-Go freezes because of its blast radius and support obligations, which do not apply here); a `preview` branch (the canary rulebook on `main` covers it without a third line to maintain); tags only (the template side needs branches for `templateUrl` anyway, and a tag cannot receive a fix); release notes generated from pull request labels ([D38](0038-release-notes-are-generated-from-pull-request-labels.md): the deploy needs a version before the release exists, the generated text covers a tag range that a floating branch blurs, and a hand-written line can say what an organization must do, which a pull request title rarely does); a rewrite commit on the engine's `v1` (two diverging histories of the same major, and every engine fix would need the rewrite again).
- **Consequences:** D38 is superseded: `.github/release.yml` is deleted, the labels stay but are not required, definition of done item 7 in the README and the pull request rules in CONTRIBUTING.md ask for a line in `RELEASENOTES.md` and a title that reads as a release line. The engine's `template/` and its fixtures say `main`; `Rulebook.Common` exports `Get-RulebookEngineRef`, `Get-RulebookSchemaUrl`, `Get-RulebookScriptUrl` and `Get-RulebookDocsUrl`, and no module holds a branch literal. The user documentation moves into the engine as `template/docs/` so both branches of the template repository are written from one source (WP13). WP13 adds the deploy, the refresh of `main`, `docs/releasing.md` and the user page on versioning. Open decision O3 ([#27](https://github.com/ALCops/rulebook-engine/issues/27)) is closed. WP14 and WP15 build any new engine URL with the helpers.
- **Affects:** WP13 ([#15](https://github.com/ALCops/rulebook-engine/issues/15)), WP14 ([#16](https://github.com/ALCops/rulebook-engine/issues/16)), WP15 ([#17](https://github.com/ALCops/rulebook-engine/issues/17)).
