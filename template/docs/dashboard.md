# The dashboard

The Publish workflow can build a small website out of your rulebook and put it at the same address as your endpoints. Each stage gets a grid with one row per rule and one column per level, and each cell shows the action that endpoint gives the rule and which input decided it. There is a page for every stage, every level and every rule, and a setup page for AL projects. From a cell you can put a change in a cart, and the cart opens an issue in your rulebook repository with the change set already filled in. The site reads your rules but never changes them: the **Apply Rulebook Change** workflow applies a submitted change set when its author may push to the repository.

## 1. What the site shows

| Page | Address | Content |
|---|---|---|
| Landing page | `<baseUrl>/` | What the site is and who it is for, in the text of `site/content/_index.md` (edit that file to say it in your own words, section 5); the facts of your rulebook (rules, analyzers, levels, stages, when it was last published, the engine version); three steps to get a ruleset into an AL project, each linking the setup page; a card per stage and per level with its description, and cards for the setup page, **How this works** and the ALCops documentation. **Open the matrix** goes to the grid of the first stage. |
| Matrix | `<baseUrl>/stages/<stage>/` | The grid of one stage: one row per rule, grouped by analyzer, in the id order of the endpoints; one column per level in settings order. The first stage of your settings (`default` in the shipped settings) is at `<baseUrl>/stages/default/`, and the stage links at the top switch between stages. A stage page also has the stage summary below the grid: the stage file, its entries with the levels where an entry has no effect, the counts per level and the ids the stage quarantines. |
| Level | `<baseUrl>/levels/<level>/` | The level file, the chain of levels it is built on, the counts per stage, and the entries of the level file grouped by analyzer, each with the action before it ("From"), the new action ("To") and its justification. Every level of your settings gets a page, your own levels included. |
| Rule | `<baseUrl>/rules/<id>/` (lowercase, for example `rules/lc0031/`) | The title, the analyzer, the default severity and whether the analyzer enables the rule by default, the documentation link, the justifications of the level and stage files that name the rule, and the cell of every level and stage. |
| Setup | `<baseUrl>/setup/` | **Set up an AL project**: one block per level (the first one open, a click opens the others) with the two commands of the init script for that level and the `al.ruleSetPath` and AL-Go `rulesetFile` lines, each with a **Copy** button (one button copies both commands); the `rulebook.json` URL; per stage a table with the endpoint URL and its **Copy** button, the number of ids it lists and a download button for the skeleton of every level, which saves the file under its skeleton name ([al-project.md](al-project.md)). The button says "Copied" for two seconds. The header and the legend link to it. |
| How this works | `<baseUrl>/how-it-works/` | One screen on what the site means: levels (each based on another, changing the action of some rules), stages (the moments a ruleset is used, such as the editor, a CI build or the next major version), the cells and their markers, and how a change from the cart becomes an issue and then a pull request in your rulebook repository. Each paragraph ends with a link to the documentation page that goes deeper. The **Help** link in the header, the landing page and the legend open it. |

A cell shows the action and a marker for the input that decided it:

| Marker | Decided by |
|---|---|
| no marker | a level file, or the analyzer default |
| dot | the stage file |
| ring | the twins rule of your settings ([pte-or-appsource.md](pte-or-appsource.md)) |
| badge `O` | an entry of `overrides.json` ([overrides.md](overrides.md)); point at the badge to see the entry's position in the file, counted from 0 |
| badge `Q` | the quarantine of the stage ([quarantine.md](quarantine.md)) |

The block **What the cells mean** below every grid repeats this legend and links to **How this works**. Point at a marker, or reach it with Tab, and a tooltip says which input it stands for. Above the grid of a matrix page are four filters: analyzer, action, the deciding input (override, quarantine, stage file, twins rule, level file, analyzer default) and a text field for the id or the title, with a row counter. The filters are stored in the address after `#`, for example `#source=override&q=LC00`, so a link with them opens the same view, and the stage links keep them when you switch stages. A bookmark of the grid made before the landing page (`<baseUrl>/#...`) now opens the landing page without the filters; open the stage and set them again.

**Every page** has a header with the ALCops logo, "Rulebook" and your organization (the owner of the repository), the **Stage** and **Level** links, **Set up**, **Help**, a dark-mode button and the cart. Below 768 px wide the links fold behind a menu button; the dark-mode button and the cart stay beside it. Under each title one sentence says what the page shows. A small **?** after a section heading of the stage, level, rule and setup pages opens the documentation of that topic. The footer shows when the site was published, the engine version that built it, a link to your rulebook repository, the link to `rulebook.json` and "Powered by ALCops". A link to a page shows its title and description when you paste it into a chat or an issue.

**Dark mode** follows the setting of your system. The button in the header switches it; the browser remembers the choice for every project site of the same `<owner>.github.io` address, until you switch back to what your system says.

**Keyboard.** A grid is one stop of the Tab key: Tab reaches its first cell, and the arrow keys move from there between the cells and the rule links at the start of each row. Home goes to the rule link of the row and End to its last cell; Ctrl+Home goes to the first rule link and Ctrl+End to the last cell of the grid. Enter or Space on a cell opens the change menu, Escape closes it and puts you back on the cell. On a narrow screen the grid scrolls inside its frame, with the header row and the rule column kept in place.

Without JavaScript the grids and pages are still complete; the filters, the popover, the cart, the dark-mode button, the menu button and the **Copy** buttons of the setup page are hidden then (select the text instead; the skeleton downloads still work), the navigation is always shown, dark mode still follows your system, and only the first cell of a grid can be reached with Tab.

## 2. Turning it on

The shipped settings have the site on:

```json
"site": { "enabled": true, "includeJustifications": false, "updateMode": "skip" }
```

1. **Pages and `baseUrl`.** The site is published the same way as the endpoints: GitHub Pages with Source GitHub Actions, at the address of the Pages site or the `baseUrl` you set ([hosting.md](hosting.md) section 2). The site needs nothing else in the repository. You do not have to install Hugo: the Publish action installs the version it pins on the runner before it builds the site.
2. **Publish.** The first run happens on the next push to `main` that changes the settings, or by hand ([hosting.md](hosting.md) section 2, step 3); Publish waits for the deployment to serve (up to about 11 minutes, [hosting.md](hosting.md#how-fast-changes-arrive) section 2, How fast changes arrive). The Publish workflow builds the site on every run while `site.enabled` is `true`. It runs on a push to `main` that changes `rulesets/`, `skeletons/`, `site/`, `catalog/diagnostics.json`, the settings or the workflow itself. A change that touches none of these does not start it: for example an override that changes no endpoint (only its justification, or an entry a more specific one hides), a quarantine edit that changes no endpoint, or a new justification in a level file. Run Actions > **Publish** > Run workflow for such a change. Until then the site shows the old state.
3. **Check.** Open `<baseUrl>/`: it shows the landing page, and **Open the matrix** the grid of the first stage. Publish already checked after the deploy that the pages of the site, `rulebook.json` and `catalog/diagnostics.json` serve what it built (every stage and level page, the setup page and the first rule page are requested); a failed check fails the run, as for the endpoints ([hosting.md](hosting.md) section 3).

With the site on, `<baseUrl>/` is the landing page, the grid of each stage is at `<baseUrl>/stages/<stage>/`, and the setup content of the plain index page moves to `<baseUrl>/setup/`. The endpoints, the skeletons and `rulebook.json` stay at their addresses, so the init script and every AL project keep working. With `"enabled": false` Publish publishes the plain index page at `<baseUrl>/`, with the setup section, and builds no site; the data files of section 6 are still published.

## 3. Changing a rule from the site

1. **Click a cell**, or reach it from the keyboard (Tab to the grid, then the arrow keys) and press Enter or Space. A popover offers the five actions `Error`, `Warning`, `Info`, `Hidden` and `None`; **Reset** only on a cell with the `O` badge (it removes the override that decides the cell); **Release** only on a cell with the `Q` badge (it releases the id from the quarantine of that stage). A stage page also has a Release button next to every id in its quarantine list. Escape closes the popover. Rule pages have the same popover.
2. **The cart** slides in from the right with the change, over the page and below the header (on a narrow screen it takes the full width), and the **Cart** button in the header shows how many changes it holds. Close it with the **×** button at its top right, with Escape or by clicking the dimmed page beside it; the **Cart** button opens it again with every change still in it. While it is open, Tab moves only through the cart, and when it closes you are back on the **Cart** button. An action becomes a change for exactly that level and stage; Reset becomes a removal of the whole override entry, with that entry's levels and stages; Release becomes a release for that stage. Per change you can:
   - tick **all levels** or **all stages** to widen it to `*` (a removal names one entry and cannot be widened); untick to go back;
   - type a justification (actions only; it goes into the override entry). The field grows as you type and takes several lines; the line breaks arrive in the issue as you typed them;
   - remove it.

   One more field, **Note for the issue**, is optional, takes several lines too and goes into the issue. A second change of the same kind for the same rule, levels and stages replaces the first. A change widened or narrowed onto the selection of another change replaces that one, and the status line says so.
3. **Before and after.** Every change lists the cells it touches, each with the action and deciding input before and after. An action shows the chosen action as an override on every matching cell. A removal or a release shows what the cell would have without the override or the quarantine, which the Publish action computed with the generator's own rules. A change that alters no cell says "No action changes: the change would be a no-op." One limit: a widened action shows the chosen action on every cell, but where a more specific override already decides a cell (an entry with exactly that level or stage), that entry still wins after the change. The pull request that applies the change shows the real result.
4. **The size.** The cart measures the issue link it will open against 7372 bytes, while you type: "`<n>` of 7372 bytes of the issue link". GitHub refuses a link of 8192 bytes or more. That fits about 28 changes with a 39-character justification each, or 46 without (a longer justification or a note fits fewer). Over the limit the text turns red and **Submit on GitHub** is disabled.
5. **Submit on GitHub** opens the issue form **Rulebook change** of your repository in a new tab, with the change set in the field **Changes** (JSON) and your note in **Note**. Read it and click **Create**; you need to be signed in to GitHub and allowed to open issues in the repository. Back on the site, the cart asks "Did GitHub open the filled form? Clear the cart?"; it is emptied only when you confirm.
6. **Too large for one link.** Over the limit the cart shows **Submit in parts**, which splits the cart into parts that fit, in the order of the changes, each with the note: every click opens the next part in a new tab ("Opened part 1 of 3."). A change that is too large for a link on its own is skipped. When every part has opened, the cart asks whether to clear it; when some were too large, the changes whose forms opened are removed from the cart and only the too-large ones stay, with the status "`N` part(s) opened and removed from the cart; `M` change(s) too large for a link stay: use Copy change set." **Copy change set** puts the whole change set on the clipboard, formatted; paste it into the **Changes** field of the empty form, which the cart links as "empty form".

The cart is kept in your browser (local storage), one cart per rulebook repository, and survives closing the tab; another browser or a private window has its own. **Clear** empties it after a confirmation.

**What happens next.** The new issue starts the **Apply Rulebook Change** workflow. It answers on the issue with one comment, and you can follow the run under Actions > Apply Rulebook Change. It needs nothing beyond the `GHTOKENWORKFLOW` secret the other writing workflows use ([ghtokenworkflow.md](ghtokenworkflow.md)).

**Who gets a change applied.** Anyone who may open an issue in the repository may submit the form. The workflow first checks the author of the issue. It applies the change set only when the author can push to the repository: the role Write, Maintain or Admin, given directly, through a team or through the organization (as GitHub's permission answer for the author reports it; not observed in a live run yet). Any other author, Read and Triage included, gets the comment "Only repository collaborators with write access can submit or edit Rulebook changes.", and the issue is closed as not planned. The change set of a refused issue is not read. An issue opened by a bot or a GitHub App is refused the same way, unless GitHub reports write access for it. A refused issue stays closed, and an edit of it does nothing. When someone other than the author edits the body, the edit is applied only when that person can push too. The editor is the person whose edit started the run, as GitHub reports it; there is nothing to configure. An edit by someone who cannot push gets the comment "The edit by `<login>` was not applied: only repository collaborators with write access can submit or edit Rulebook changes. The issue stays open; its author can edit the body to run the workflow again." The issue stays open, and nothing is written. A maintainer who wants to apply its change set opens a new issue with it (**Copy change set** in the cart, or the **Changes** field of the refused issue).

**The label.** The form asks GitHub for the label `rulebook-change`. GitHub ignores a form label that does not exist in the repository (observed in the live run of 2026-10-18). The workflow therefore creates the label when it handles the first submission whose body it could read from an author who may push, and adds it to the issue. You do not create it yourself. A refused issue and an issue whose body could not be read get no label.

**One pull request per issue.** The workflow reads the **Changes** and **Note** fields and checks the change set. It applies every change at once, regenerates the endpoints and validates the result before anything is pushed. It then pushes the branch `rulebook-change/<issue>/<yyMMddHHmmss>` (UTC) and opens one pull request for the whole change set. The title is the change and the issue number, for example `Change LC0015 to None (levels: strict, stages: ci) (#12)` or `Rulebook change: 3 changes (#12)`. The body has the note of the issue when there is one, the before and after table of every change ([changing-a-rule.md](changing-a-rule.md) section 4), and `Closes #12` at the end. The comment on the issue is `Pull request: <link>` followed by the same body without the `Closes` line. The issue stays open until the pull request is merged, and the merge closes it. The pull request is opened with the secret, so Validate runs on it.

**Direct commit.** With `commitOptions.createPullRequest` set to `false` in the settings, the change is committed to the default branch instead ([changing-a-rule.md](changing-a-rule.md) section 6). The comment is `Committed to <branch> (<link to the commit>)` followed by the same tables, and the issue is closed as completed. When branch protection or a ruleset refuses the push, the workflow opens the pull request instead, and the first line of the comment ends with "(the direct commit was refused)".

**Errors.** When the body cannot be read or a change is not valid, nothing is written. Examples are JSON that does not parse, a change the change set schema does not allow, an id that is not in your catalog, a level or stage that is not in your settings, a change repeated in the set, or a removal of an entry that does not exist. One comment lists every error, one line each. It starts with "The change set could not be read:" (the body, the JSON or the schema) or "The change set is not valid; nothing was written." (the catalog, the settings or the files), and ends with "Edit the issue body to run it again." When the changed rulebook would not pass validation, the comment starts with "The changed rulebook would not validate; nothing was pushed." The issue stays open and the run is red. Fix the **Changes** field and save the body: the workflow runs again.

**Nothing to change.** When no change of the set would change anything ([changing-a-rule.md](changing-a-rule.md) section 5), the comment is "Nothing to change." with one line per change, and the issue is closed as completed. A long list ends with a line that says how many more items are in the job log. Nothing is written, and the secret is not needed. When the default branch received the same change while the workflow ran, the comment is "Nothing to change: `<branch>` already holds this change.", and the issue is closed as completed too.

**A second run while the pull request is open.** An edit of the body while the pull request of the issue is open gets the comment "The pull request already exists: `<link>`. Edits of this issue are not applied to it; close the pull request first to apply the edited change set." Nothing else happens. Change the pull request itself, or close it and edit the body again.

**When the workflow runs.** It runs when an issue is opened, and when the body of an open issue is edited. A change of the title alone may still start a run; it posts nothing new. A run never posts the same comment twice in a row: when the latest comment of the issue is the workflow's own with the same text, the run shows a notice instead. Adding a label or a comment starts nothing. It works only on an issue with the label `rulebook-change`, or with both headings `### Changes` and `### Note` in the body. An issue from the form shows each field as a heading with the field's label (`### Changes`, `### Note`), an empty Note as "_No response_" (observed in the live run of 2026-10-18). That is how a new issue from the form is recognised before it has the label. A blank issue that you write with both headings is treated as a submission too. A closed issue is skipped without a comment, so an edit of a refused or closed issue does nothing. When the body changes again before a run reads it, that run stops without a comment, and the run of the newer edit applies the latest body; Actions shows the first run as done without a change.

**The secret.** The push and the pull request use the `GHTOKENWORKFLOW` secret. When it is missing, a valid change set gets the comment "The change set is valid, but the GHTOKENWORKFLOW secret is missing or cannot be used, so nothing was pushed (the secret is empty or not set). A maintainer sets it as described in https://github.com/ALCops/rulebook/blob/main/docs/ghtokenworkflow.md; then edit the issue body to run it again." The run is red and the issue stays open. When the push or the pull request fails, the comment starts with "Failed to push the change set." or "Failed to create the pull request for the change set.", shows the error with the token or the secret replaced by `***`, and ends with "Edit the issue body to run it again."

**Other failures.** When the run fails with an unexpected error after it read the issue and before anything was written, the comment is "The Apply Rulebook Change run failed before the change was written; see the job log (`<link to the run>`)." If GitHub could not be read or written (the issue, the author's permission, a comment), there is no comment and the red run shows the error. Read the error in the run, then edit the body to run it again. A failure of the workflow's own step "Read the settings" happens before the change set is handled and leaves no comment; the red run shows it.

Every op is applied by the workflow, in the one pull request or commit with the regenerated endpoints:

| `op` in the change set | What the workflow writes |
|---|---|
| `set` (an action) | The override entry in `overrides.json` for the id, levels and stages, with the justification. An entry with the same levels and stages is replaced ([overrides.md](overrides.md)). |
| `remove` (Reset) | Deletes the override entry with exactly these levels and stages, also an entry with two or more levels or stages, which the Change Rule form cannot select. |
| `release` | Removes the id from `quarantine.<stage>.json` of every stage it names ([quarantine.md](quarantine.md) section 4). The file is written in the template's layout, one entry per line, so a quarantine file you formatted by hand is normalised. |

The site shows the new state after the pull request is merged (or the commit is pushed) and Publish has run. For a change that changes no endpoint, such as a new justification, run Publish by hand (section 2).

## 4. What is public

Anyone who can open the site sees the action of every rule on every endpoint, and which input decided it. On GitHub Free a Pages site is public, and so are the endpoints in every case: the AL compiler reads them without signing in. The site adds this:

| Data | On the site | Why |
|---|---|---|
| The action of every rule on every endpoint | yes | The endpoints and the analyzer defaults say the same. |
| The deciding input of every cell (override, quarantine, stage, level, twins, default) | yes | It shows that you deviate, not why. |
| The justifications of the level and stage files, the shipped ones and your own | yes, always | The shipped files are public in the engine; your own level and stage files are part of the rulebook the site describes. |
| The justification text of your overrides and quarantine entries | only with `"includeJustifications": true` | Free text your organization wrote; a quarantine justification names package versions and dates. |

If the repository itself is public, which GitHub Free requires for Pages, `overrides.json`, the quarantine files and their justifications are readable there anyway; `includeJustifications` only matters when the repository is private (paid plans).

With `includeJustifications` set to `true`, the override justifications are written into `rulebook.json` and the quarantine justifications also appear in the quarantine list of the stage pages. Any other value leaves both out. There is no other access control on the site. If none of this should be on a web page, set `"enabled": false`: Publish keeps the plain index page, and `rulebook.json` and `catalog/diagnostics.json` are still published, with the same rule for the justifications.

## 5. Adapting `site/`

`site/` holds the whole site: `hugo.yaml` (the title), `content/` (the pages and their descriptions), `layouts/` (the HTML of every page; `partials/logo.html` is the logo of the header, `how-it-works/single.html` the text of **How this works**, which takes its documentation links from the `docs` of the data file), `assets/css/site.css` (the design tokens at the top), `assets/js/` (the dark-mode button and the menu, the filters, the popover and the cart) and `static/` (`favicon.svg` and `favicon.png`). It uses no theme, no npm, no web font and no framework. You can change any of these files.

**The tokens.** The colours of the site are variables at the top of `site.css`, in three blocks: the light set under `:root`, the dark set under `[data-theme="dark"]` (the dark-mode button) and the same dark set again inside `@media (prefers-color-scheme: dark)` (the system setting). Change both dark blocks the same way. The ones an organization usually changes:

| Token | Used for |
|---|---|
| `--accent`, `--accent-text`, `--accent-soft` | links, the current stage and level, the cart count; `--accent-text` is the text on `--accent` |
| `--bg`, `--surface`, `--surface-2`, `--line`, `--line-strong` | the page, the header and footer, the group rows of the grid, the borders |
| `--text`, `--muted`, `--brand` | body text, secondary text, the logo and "Rulebook" |
| `--error`, `--warning`, `--info`, `--hidden`, `--none` and their `-bg` pairs | the action chips of the grid |
| `--override`, `--quarantine`, `--mark-text` | the `O` and `Q` badges |
| `--shadow`, `--scrim` | the shadow of the popover and the cart, the dimmed page beside the open cart |
| `--font`, `--mono` | the system font stack and the monospace font of ids and chips |

Keep a text colour and its background at a contrast of at least 4.5:1 (WCAG AA), in both sets. To use your own logo, replace the SVG in `layouts/partials/logo.html` (keep `fill="currentColor"` to follow the colour scheme) and the two favicons in `static/`.

**Updates.** `site/` is a customizable file class, like `docs/` ([updating.md](updating.md) section 1). The update replaces a site file you have not changed. A file you changed is kept, and when the template changed it too, the update pull request lists it under "Skipped: local changes" with a link to the template diff, so you can take over what you need. A site file you deleted comes back while the template ships it, unless you list it in `unusedRulebookFiles`. With `site.updateMode` set to `"overwrite"` the template's files always replace yours.

A file you changed and the update kept keeps running against a newer `rulebook.json` and the template's newer scripts, so it can break after an update. The safest changes are the title in `hugo.yaml` and the tokens at the top of `site.css`. If you change `layouts/` or `assets/js/`, check the "Skipped: local changes" list of every update pull request and build the site locally before you merge it.

**The landing text.** The text of `<baseUrl>/` is `content/_index.md`: `title` is the heading, `description` the sentence under it (and the description a chat shows for a link to the site), and the paragraphs below the front matter are the body, in Markdown. Change them there; the layout `layouts/index.html` adds the facts, the steps and the cards from the data file. If you edited `content/_index.md` before the landing page came, the update keeps your file with its old front matter (`title: Matrix`, no body); take the new text from the template diff the update pull request links.

**What the site needs.** Publish builds whatever `site/` holds. Keep these parts when you change a layout:

- the attribute `data-rulebook-matrix` on the grid of the first stage, `<baseUrl>/stages/<stage>/` (the `section` in `layouts/partials/matrix.html`). Without it Publish warns that `site/layouts` may have dropped the matrix, names the page it checked, and still publishes the site as built;
- the attributes `data-repository`, `data-issue-template` and `data-rulebook-json` on `<body>` (`layouts/baseof.html`), the `cart` partial (the cart, its close button and the overlay behind it) and the `popover` partial, and the cart button in the header: the cart needs them to work;
- `role="grid"` on a grid table and `tabindex` on its cells (`layouts/partials/cell.html`): the keyboard route needs them.

**Building it locally.** You need Hugo 0.156.0 or later, extended, and a data file in `site/data/rulebook.json`. The quickest data file is the published one: download `<baseUrl>/rulebook.json` into `site/data/`. To see changes you have not published yet, write the file from a clone of the engine ([ALCops/rulebook-engine](https://github.com/ALCops/rulebook-engine)) instead. Run it in the root of your rulebook repository: `Export-RulebookSiteData` reads `.github/Rulebook-Settings.json` and `catalog/diagnostics.json` there and throws without them. Pass `-Repository` with your repository as `owner/name`, or the cart cannot build the issue link:

```powershell
Import-Module <engine clone>/modules/Rulebook.Site.psd1
Export-RulebookSiteData -RepositoryRoot . -BaseUrl https://contoso.github.io/rulebook -Repository contoso/rulebook
hugo --source site --baseURL https://contoso.github.io/rulebook/ --destination <folder outside the repository> --noBuildLock
```

To click through the result, build with `--baseURL http://localhost:8000/` instead and serve the folder with any local web server on that port, for example `python -m http.server 8000` in the folder: the links of the pages start with the path of `--baseURL`. `site/data/` and the build output are in `site/.gitignore`; they are never committed, and the update never touches `site/data/`.

## 6. The data files

Publish writes two files for other tooling (scripts, an editor extension, a report) on every run, with or without the site:

| File | Content |
|---|---|
| `<baseUrl>/rulebook.json` | One document with everything the site shows. The keys in order: `generatedAt`, `repository`, `baseUrl`, `issueTemplate`, `docsUrl`, `initScriptUrl`, `engineRef` and `alProjectDocsUrl` (the links and the engine ref of the setup page), `docs` (the documentation link of each topic the site links, and `home`, the ALCops site of the footer), `levels` (settings order, with the facts, counts and entries of each level page), `stages` (the same for the stage pages), `rules` (every id with its default and one cell per level and stage: `action`, `source`, and on override and quarantine cells the `fallback` the cart uses), `overrides` (the entries of `overrides.json` in file order) and `quarantine` (one list per stage). The init script reads the `levels` and `stages` names and slugs. |
| `<baseUrl>/catalog/diagnostics.json` | Your `catalog/diagnostics.json`, byte for byte. |

`generatedAt` is UTC text such as `2026-10-17T08:30:00Z`. PowerShell's `ConvertFrom-Json` turns it into a date; read it with `ConvertFrom-Json -DateKind String` (PowerShell 7.5 and later) to keep the text. The complete key list with an example is section 5 of the engine's [dashboard.md](https://github.com/ALCops/rulebook-engine/blob/main/docs/dashboard.md).

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Publish fails with failure `site`: "Installing Hugo ... failed: ..." | The Hugo download, its download check (sha256) or the install failed, or the runner is not Linux and has no extended Hugo 0.156.0 or later (the message names `hugoPath`, an input of the Publish action). | Run Publish again on `ubuntu-latest` as shipped; elsewhere install Hugo 0.156.0 or later (extended) and pass its path as `hugoPath`. If it keeps failing, set `site.enabled` to `false` to publish the plain index page meanwhile. |
| Publish fails with failure `site`: "The site build failed: ..." | Hugo could not build `site/`, often after a change to a layout. The red error in the run summary carries the end of Hugo's output; the previous deployment stays live. | Fix the file Hugo names (build locally, section 5) or restore it from the template. |
| Publish fails with failure `site`: "site.enabled is true, but Hugo was not found ..." | `hugoPath` (an input of the Publish action) names a Hugo that is not there. | Correct `hugoPath`, or remove it so the action installs its Hugo. |
| Warning "site.enabled is true, but site/hugo.yaml is missing: this run publishes the plain index.html. ..." | The repository has no `site/` yet (created before the template shipped it), or the file was deleted. | Run **Update Rulebook System Files** to get `site/`, or set `site.enabled` to `false`. |
| Warning "The built stages/default/index.html has no data-rulebook-matrix marker: ..." (the page of your first stage) | A changed layout no longer carries the attribute (section 5). | Put `data-rulebook-matrix` back on the grid, or ignore the warning if you dropped the matrix on purpose. |
| GitHub shows an error page (500, 502 or 414) after Submit | You are not signed in: GitHub sends you to the sign-in page with the whole link appended, and that redirect fails from about 7 KB with 500 or 502. A signed-in browser gets 414 "URI Too Long" from 8192 bytes, which the cart's 7372-byte limit stays under. | Sign in to GitHub first and submit again; or use **Submit in parts** or **Copy change set** with the empty form. |
| The byte count is red and Submit on GitHub is disabled | The issue link would be more than 7372 bytes. | **Submit in parts**, or **Copy change set** and the empty form; shorter justifications and a shorter note also help. |
| The cart is empty after a submission | You confirmed "Did GitHub open the filled form? Clear the cart?". Or you opened the site in another browser or a private window, which keeps its own cart. | If the form did not open, add the changes again. Submitted issues keep the change set. |
| A filter is gone after a click | Only the stage links keep the filters; the level, rule and other links do not. | Go back in the browser, or open a link that carries the part after `#`. |
| A cell has no Reset | Reset removes an override, and only a cell with the `O` badge is decided by one. A cell with the ring is decided by the twins rule, which may follow an override on the other rule of the pair. | Choose an action for the cell instead, or reset the override on the cell that carries the badge. |
| The issue got no comment | The workflow did not run: the issue has neither the label `rulebook-change` nor both headings `### Changes` and `### Note` in its body, or Actions are disabled for the repository. Or only the title was edited, or the edit left the body as it was ("The issue body did not change; nothing to do."), or the answer would repeat the latest comment of the workflow ("The comment was not posted again: ..."): such a run posts nothing new. Or the run is red because it could not read the issue or a permission from GitHub, which gives no comment, or the workflow's own step "Read the settings" failed (it leaves no comment either). | Open the issue from the cart, or use the form **Rulebook change** and paste the change set. Check Actions > Apply Rulebook Change for a run, and read the annotation of a red run. To run it again on the same issue, edit the body. |
| The issue has no label `rulebook-change` after the run | The author or the editor was refused, the body could not be read, or the workflow could not add the label. The last case is a warning in the run, and the change set is applied all the same. | Nothing to do for a refused or unreadable issue. Otherwise add the label by hand if you filter issues by it. |
| "Only repository collaborators with write access can submit or edit Rulebook changes." and the issue is closed as not planned | The author of the issue cannot push to the repository: Read or Triage access, no access, a bot or a GitHub App (section 3). | Ask for write access and open a new issue, or hand the change set to a maintainer (**Copy change set**), who opens a new issue. An edit of the closed issue does nothing. |
| "The edit by `<login>` was not applied: only repository collaborators with write access can submit or edit Rulebook changes. ..." and the issue stays open | Someone other than the author edited the body and cannot push to the repository (section 3). Nothing was written. | The author edits the body to run the workflow again, or the editor asks for write access. |
| "The change set is valid, but the GHTOKENWORKFLOW secret is missing or cannot be used, so nothing was pushed (...)" | The secret is not set, this repository cannot see it, or the token in it cannot be used. | A maintainer sets it ([ghtokenworkflow.md](ghtokenworkflow.md)); then edit the body of the issue. |
| The run is red and the comment starts with "The change set could not be read:", "The change set is not valid; nothing was written." or "The changed rulebook would not validate; nothing was pushed." | The submission has an error; the comment has one line per error (section 3). | Fix the **Changes** field and save the body, or open a new issue from the cart. |
| "The pull request already exists: ..." | The pull request of this issue is still open, and an edit of the body is not applied to it. | Change that pull request, or close it and edit the body again. |
| "Failed to push the change set. Make sure that the token in the secret GHTOKENWORKFLOW is not expired ..." or "Failed to create the pull request for the change set. ..." | The token cannot write contents or pull requests, or has expired. | Renew it or add the permission ([ghtokenworkflow.md](ghtokenworkflow.md) section 6), then edit the body of the issue. |
| "The base branch moved since the change was planned (...); nothing was pushed. ..." | Someone pushed to the default branch while the workflow was working. | Edit the body of the issue to run it again. |
| "The Apply Rulebook Change run failed before the change was written; see the job log (...)." | An unexpected error; the job log has it. | Read the error in the run, then edit the body of the issue to run it again. |
| The cart says "The data file names no repository as owner/name, so the site cannot open its issue form." | The site was built from a `rulebook.json` without `repository`, for example a local build without `-Repository`. | Publish writes it on GitHub; for a local build pass `-Repository` (section 5). |
| The cart says "rulebook.json could not be read, so the before and after are not shown." | The page could not load `<baseUrl>/rulebook.json`, for example while the deploy is running. | Reload the page; the next action tries again. |
| The site still shows the old state after a merge | The change touched no path the Publish workflow runs on (section 2), or the deploy is a few seconds old. | Run Publish by hand; GitHub Pages may serve a file from its cache for up to 10 minutes. |
